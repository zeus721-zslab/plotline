## D-01 백엔드 FastAPI (2026-10-08)
- 결정: 관리자 API(스키마·검증·승인·버전·발행)를 Python FastAPI로 구현한다.
- 근거: 데이터 수집·정제 파이프라인과 같은 언어(Python)로 통일하고, 작업 범위를 Python 백엔드까지 넓힌다.
- 대안: Laravel (데이터 파이프라인과 언어 통일·작업 범위 확장 목적에 불리해 기각)

## D-02 프론트 SvelteKit·Svelte 5 (2026-10-08)
- 결정: 프론트는 SvelteKit + Svelte 5(runes)로 만든다.
- 근거: 스크롤리텔링·데이터 스토리 분야의 참고 자산이 SvelteKit에 집중되어 있고, 관리자 SPA까지 한 앱으로 처리할 수 있다.
- 대안: Nuxt·Astro (참고 자산이 적고 스토리·관리자 화면을 한 앱으로 묶기 불리해 기각)

## D-03 DB 공유 MariaDB 10.11 재사용 (2026-10-08)

- 대안: PostgreSQL·전용 DB (컨테이너 추가로 서버 RAM 사용이 늘어 기각)

## D-04 첫 스토리 원소 발견사 (2026-10-08)

## D-05 스토리 구성 파일 JSON (2026-10-08)

## D-06 관리자 인증: 단일 계정 + 세션 쿠키 + 로그인 rate limit (2026-10-08)

- 근거: 1인 운영이라 다중 사용자·권한 관리가 필요 없고, 시크릿은 .env로만 관리한다.

## D-07 프론트 adapter-static, 스토리 데이터는 발행 시 정적 JSON (2026-10-08)

- 근거: 운영에 Node 프로세스가 필요 없어 RAM과 관리 대상이 줄고, 공개 페이지는 정적 파일로 서빙된다.
- 대안: Node SSR (운영 프로세스·RAM이 늘어 기각)

## D-08 운영 네트워크: infra_net(DB) + gateway_net(프록시)만 사용 (2026-10-08)
- 결정: 운영 컨테이너는 공유 네트워크 infra_net(DB 접근)과 gateway_net(gateway nginx 프록시)만 사용한다.
- 근거: 공유 인프라 재사용 구조를 따르고, 프로젝트 전용 네트워크·포트 노출을 늘리지 않는다.

## D-12 PR CI: 단일 워크플로 · 경로 필터 없음 (2026-10-08)

- 근거: 두 잡을 main 보호 규칙의 필수 체크로 지정하기 위해 항상 결과가 남아야 한다.
- 대안: 경로 필터로 변경 영역만 실행 (변경 없는 쪽 필수 체크가 대기 상태로 남아 기각)

## D-13 운영 컨테이너: web(nginx 정적+프록시) · api(FastAPI) 2개 (2026-10-08)
- 결정: 운영은 web(nginx: 정적 파일·/data 서빙·/api 프록시)과 api(FastAPI) 2개 컨테이너로 구성하고, gateway는 web만 바라본다. 공유 네트워크 충돌을 피하려고 별칭·컨테이너 이름은 plotline-web · plotline-api로 고정한다.
- 근거: gateway 블록이 upstream 1개로 단순해지고, 경로 라우팅이 저장소 안 설정으로 관리된다. nginx 추가 메모리는 수 MB 수준.
- 대안: gateway가 정적·/api를 각각 라우팅 (gateway 설정이 프로젝트 경로 구조에 묶여 기각)

## D-14 발행 데이터: 런타임 볼륨 (2026-10-08)
- 결정: 발행 시 api가 정적 JSON을 공유 볼륨(published)에 쓰고, web이 /data/ 경로로 읽기 전용 서빙한다.
- 근거: 관리자 입력 → 승인 → 발행 흐름이 배포 없이 끝난다. 볼륨은 DB의 승인 버전으로 재생성할 수 있다.
- 대안: 발행 결과를 저장소에 커밋해 이미지에 포함 (데이터 수정마다 PR·배포가 필요해 기각)

## D-15 배포: 방식 A + 배포 잡 활성화 변수 (2026-10-08)
- 결정: main push 시 변경된 서비스 이미지만 GHCR에 빌드·push하고, 서버 배포는 SSH로 scripts/deploy.sh를 호출한다. 배포 잡은 저장소 변수 DEPLOY_ENABLED가 true일 때만 실행한다.
- 근거: 기존 서버의 방식 A를 재사용하고, 서버 준비(키·디렉터리·.env·gateway) 전에 머지해도 배포 실패가 나지 않게 한다. 서버 명령을 저장소 스크립트로 두어 워크플로를 얇게 유지한다.
- 대안: 서버 준비 후 워크플로를 별도 PR로 추가 (연관 변경이 PR 2개로 나뉘어 기각)

## D-18 출처 규칙(기획서 §4-2 "출처 필수" 수정): 행마다 출처 유형(external/self) 필수. external은 URL·기준 날짜 필수, self는 불필요하며 화면에 "직접 작성" 표시. Claude 데이터화 경로는 external만 허용 (2026-10-08)

## D-19 운영 마이그레이션 적용: 배포 시 자동 실행. deploy.sh가 새 api 기동 전에 alembic upgrade head를 1회 실행하고, 실패하면 배포를 중단해 기존 컨테이너를 유지한다. 한 번의 배포에는 추가형 변경만 넣는다 (2026-10-08)

- 대안: 수동 실행 — 누락 시 500 위험으로 기각 · 컨테이너 시작 시 자동 실행 — 재시작마다 실행되고 실패 시 api 기동 불가로 장애 범위가 커 기각

## D-20 관리자 인증: 단일 관리자, .env 계정(argon2id 해시) + 서명된 세션 쿠키(HttpOnly·Secure·SameSite=Strict·8시간), 상태 변경 요청 Origin 검사, 설정 누락 시 로그인 비활성(fail closed) (2026-10-08)
- 근거: 관리자 1명에 필요한 최소 구성. 쿠키는 스크립트에서 읽을 수 없고, 인증 경계가 앱 안에 있어 테스트로 검증 가능
- 대안: JWT 브라우저 저장 — XSS 노출로 기각 · nginx Basic 인증 — 로그아웃 없음·앱 내 경계 없음으로 기각 · GitHub OAuth — 구성 요소 과다로 기각

## D-21 프록시 헤더 신뢰 제거: uvicorn --proxy-headers · --forwarded-allow-ips="*" 제거 (2026-10-08)
- 근거: 앱이 클라이언트 IP·스킴을 쓰지 않으며, 모든 출처를 신뢰하는 설정은 헤더 위조 여지만 남김
- 대안: 신뢰 대역을 web 컨테이너로 축소 — 쓰지 않는 기능을 위한 설정 유지라 기각

## D-22 관리자 인증 보강(외부 검토 1R 반영): 동시 검증 초과 시 429(대기 없음) · 비밀번호 해시 지문을 서명 salt에 포함해 비밀번호 교체 시 세션 무효 · 허용 Origin 형식·해시 비용 범위 검사로 설정 오류 시 비활성 · --no-proxy-headers 명시 · 끝 슬래시 리다이렉트 끔 · 관리자 응답 no-store (2026-10-08)
- 근거: 검증 대기로 인한 스레드풀 고갈 차단, 비밀번호 유출 대응 시 세션 잔존 방지, 운영 설정 실수를 fail closed로 드러냄
- 대안: 세마포어 대기 유지 + gateway 제한에만 의존 — gateway 반영 전 노출 구간이 있어 기각 · 비밀번호 교체 시 SESSION_SECRET 동시 교체를 절차로만 강제 — 실수 여지가 남아 기각
- 외부 검토: A / Fable 1R / 지적 10건 중 수용 9 · 부분 1

## D-23 관리자 인증 보강(외부 검토 2R 반영): 설정 오류 로그는 기동 시 1회 · 검증 오류(422) 응답에서 입력값 제거와 no-store · 구조 테스트에 /api 동적 경로 금지·WebSocket 존재 금지·실제 라우팅 역검증 추가 (2026-10-08)
- 근거: 요청을 이용한 로그 증폭 차단, 비밀번호가 오류 응답으로 되돌아가는 것 방지, 구조 테스트가 놓치는 매칭 경로 보완
- 대안: WebSocket 경로까지 순회하는 검사 — 현재 WebSocket을 쓰지 않아 존재 금지로 대체
- 외부 검토: A / ChatGPT 2R / 지적 4건 중 수용 3 · 부분 1 (외부 검토 종료)

## D-24 DB 테스트 구조: 테스트 전용 MariaDB 컨테이너(db-test, tmpfs) + 세션당 마이그레이션 1회 + 테스트별 트랜잭션 롤백 (2026-10-09)
- 근거: 운영과 같은 DB 엔진으로 JSON·collation·제약 동작을 확인하면서 테이블 재생성 없이 테스트 시간을 짧게 유지하고, 개발 데이터와 분리한다
- 대안: 개발 DB 컨테이너에 테스트용 database 추가 — 기존 볼륨에는 초기화 스크립트가 적용되지 않고 계정 권한 추가가 필요해 기각 · SQLite — JSON·ENUM·collation 동작이 달라 기각

## D-25 스토리 이미지: 퍼블릭 도메인 그림(역사 인물 초상화 포함) + 코드로 그린 SVG만 사용 (2026-10-09)
- 결정: 기획서 §4-2 "인물 사진은 쓰지 않는다"를 조정해, 저작권이 끝난 역사 인물의 초상화·옛 그림은 허용한다. 사진과 현대 인물 이미지는 계속 쓰지 않는다. 이미지는 위키미디어 커먼즈의 퍼블릭 도메인·CC0 만 쓰고, 출처·라이선스를 화면에 표시하며, 저장소에 휴대폰용 크기로 넣어 직접 서빙한다
- 근거: 원래 원칙은 루머·사생활 위험이 있는 현대 실존 인물을 겨냥한 것이다. 수백 년 전 과학자의 공개 초상화는 위험이 낮고 이야기 몰입을 크게 높인다. 외부 링크 대신 직접 서빙해 성능과 가용성을 통제한다

- 결정: 여러 스토리가 함께 쓰는 코드는 frontend/src/lib/story/, 한 스토리 전용 코드는 frontend/src/lib/stories/<스토리 slug>/ 에 둔다. 공통은 전용을 import 하지 않는다(표지 카드는 2편 작업에서 정리). 발행 계약의 question 은 선택 항목이고 없으면 화면은 title 을 쓴다. 스토리 화면의 출처는 기본 접힘으로 두고 누르면 펼친다
- 근거: 2편 착수 전에 공통 · 전용 경계를 디렉터리와 import 방향으로 드러내 재사용 범위를 확인한다. 2편부터 표지 질문 문장을 쓰지 않는다. 출처 목록이 길어 스토리 끝이 늘어진다는 사용 피드백
- 대안: 한 폴더에 두고 파일 이름으로 구분 — 경계가 import 로 드러나지 않아 기각 · question 을 빈 문자열로 유지 — 빈 값의 의미가 모호해 기각

## D-27 관리자 데이터 입력 — 정의 + 행 묶음 붙여넣기 · 일괄 승인 · 버전 구성 규칙 (2026-10-09)
- 결정: 붙여넣기는 {"fields"?, "rows"} JSON 묶음 하나로 받는다. 묶음의 정의가 최신과 다르면 관리자 확인 후 새 정의 버전으로 저장하고 같은 트랜잭션에서 행을 넣는다. 승인은 오류 없는 대기 행 일괄 승인 + 행별 반려(대기 → 승인/반려만). 버전은 최신 정의로 들어온 승인 행 중 key 마다 가장 최근 행으로 구성한다
- 근거: Claude 데이터화 결과를 한 번에 옮겨 정의를 손으로 입력하지 않는다(운영자 부담 최소화). 정의가 다른 행이 한 버전에 섞이지 않게 한다. 값 수정은 새 입력으로 하고 버전이 최신 행을 고른다
- 대안: 행만 붙여넣고 정의는 화면에서 입력 — 데이터셋마다 정의를 손으로 쳐야 해 기각 · 행별 승인 버튼만 — 행이 수백 개면 운영 부담이 커 기각 · 승인 취소 · 행 수정 기능 — 새 입력 + 최신 행 선택으로 대체 가능해 기각

## D-28 관리자 재설계: 목록 + 데이터 묶음 작업 페이지 · 붙여넣기 확인 후 저장 · 줄 상태 규칙(대체됨 · 변화 없음 건너뜀 · 확인일만 갱신 분리 · 구조 이월 · 구분 칸 단위 공개 제외) (2026-10-09)
- 결정: 운영자는 목록의 붙여넣기 칸과 묶음 작업 페이지(붙여넣기 → 검사 · 승인 → 발행, 위→아래)만 쓴다. 붙여넣기는 미리보기로 대상 · 구조 변화 · 줄 분류를 확인한 뒤 저장하며, 미리보기와 저장은 같은 계획 함수를 쓴다. 같은 구분 칸의 새 줄이 들어오면 옛 대기 줄을, 새 줄이 승인되면 옛 승인 줄을 대체됨으로 바꿔 구분 칸마다 승인 줄 · 대기 줄이 각각 1개를 넘지 않게 한다. 현재 승인 줄과 값 · 출처가 같은 줄은 저장하지 않고, 확인한 날만 다른 줄은 따로 묶는다. 구조가 바뀌면 승인 줄을 새 구조로 재검사해 통과는 승인, 실패는 오류 대기로 새 줄을 만들고 원본은 대체됨으로 둔다. 공개 제외는 구분 칸 단위로 기록본에서 빼고 복원할 수 있다. 구조가 바뀌면 옛 구조로 들어온 대기 줄은 모두 대체됨으로 두고, 승인은 최신 구조로 들어온 줄만 받는다. D-27 의 정의 직접 입력 · 빈 묶음 생성 · 입력별 승인 · 수동 기록본 화면을 대체한다
- 배포: 스키마 변경은 추가형이지만, 새 코드가 대체됨 상태를 한 번이라도 쓰면 이전 이미지는 그 값을 읽지 못한다(Enum 매핑). 첫 대체 이후에는 전진 배포만 하고, 롤백이 필요하면 코드 수정으로 전진한다
- 근거: 실제 흐름은 Claude 묶음 붙여넣기에서 시작하므로 단계별 페이지는 되돌아가기만 만든다. 구조 변경 때 승인 데이터가 조용히 빠지는 일과 삭제 수단 공백을 막는다. 반복 붙여넣기에서 검토할 줄을 실제 변화로 줄인다
- 대안: 단계별 페이지 · 탭(정의 → 입력 → 검토 → 기록) — 운영자 시나리오에서 되돌아감이 많아 기각 · 구조 이월 없이 새 구조 승인 줄만 기록본에 포함 — 승인 데이터가 조용히 빠져 기각 · 줄 직접 삭제 — 이력이 사라져 공개 제외로 대체
- 외부 검토: A / Fable 1R / 지적 9건 중 수용 6 · 부분 1 (2R 생략: 기존 잠금 방식 재사용, 셀프 리뷰 새 지적 없음)

## D-29 발행: 기록본 생성과 공개 파일 쓰기를 한 동작으로 한다 (2026-10-09)
- 결정: 발행 = 기록본 생성(DB 커밋, 상태 pending · 파일 해시) 후 파일 쓰기, 결과로 상태 done/failed. 파일은 같은 폴더 임시 파일 → 하드 링크로 최종 경로 배타적 생성(덮어쓰기 없음). 같은 내용이면 성공(재시도 멱등), 다른 내용이면 failed. 미완료(pending/failed) 기록본이 있으면 새 발행을 막고 재시도부터. 승인 후보 0 이면 발행 차단 — 데이터를 공개에서 내리는 일은 이야기 파일 작업으로 본다. 기록본만 만드는 API 는 제거. 발행 줄 순서는 구분 칸 값 순.
- 근거: 공개 파일 불변(이야기가 판 번호로 참조) · 재시도 안전 · 빈 파일로 이야기 화면이 깨지는 것 방지 · 판 번호 구멍 방지.
- 대안: rename 덮어쓰기(불변 깨짐, 기각) · 파일 먼저 쓰고 DB 커밋(커밋 실패 시 고아 파일, 기각) · 미완료를 두고 다음 판 발행(판 번호 구멍, 기각) · 빈 데이터 파일 발행(이야기 화면 깨짐, 기각).

## D-30 발행 기록본 폐기와 내용 오류 처리 (2026-10-09)
- 결정: 미완료(pending · failed) 기록본은 폐기(abandoned)로 끝낼 수 있다. 폐기는 번호를 소진하고 줄 · 파일은 건드리지 않는다(이미 있는 파일도 삭제 · 이동하지 않음). 변화 없음 · 공개본 대비 비교는 마지막 done 기록본 기준. 직렬화 사전 검사(빈 줄 · 값 형식 · 인코딩 · 정렬)를 통과하지 못하면 발행은 커밋 전 409, 재시도는 failed(content_invalid). 재시도에서 재생성 바이트가 저장 해시와 다르면 덮어쓰지 않고 failed(content_changed). done 인데 파일이 없으면 저장 해시와 같은 바이트일 때만 다시 쓴다. 강제 완료는 두지 않는다.
- 근거: D-29 는 미완료를 재시도로만 끝낼 수 있어, 재시도가 구조적으로 실패하면 묶음 발행이 영구히 막혔다. 폐기는 공개 URL 의 바이트를 건드리지 않아 불변 원칙과 맞고, 번호 구멍은 폐기 기록으로 설명된다.
- 대안: 파일 이동 후 재시도(공개 바이트 변경, 기각 — 필요 시 운영 수작업 예외로만) · 강제 완료(DB 스냅샷과 공개본 불일치 영구화, 기각) · 재시도 때 해시 덮어쓰기(결정성 깨짐 신호 소실, 기각).
- 외부 검토: A / Fable 1R 지적 7건 중 수용 6 · 부분 1(R-01 드라이런은 운영 기록본 0건이라 기각) / 2R 지적 4건 중 수용 4(파일 존재 표시 · 내용 오류 분류 · 직렬화 골든 테스트 · 건너뜀 수 분리)

## D-31 2편 빛의 나이 데이터 구조 · 표시 규칙 · 사건 대조 (2026-10-09)
- 결정: sky_objects 는 거리를 출처 원래 값(distance_value number + distance_unit km|광년)으로 저장하고, 반올림 · 한글 단위(만 · 억 · 조) · 빛 이동 시간은 화면에서 계산한다(빛의 속도 299,792.458 km/s, 저장 안 함). show_exact=true 면 반올림하지 않고 쉼표 원래 값을 보인다(보이저 1호). distance_note 는 출처 값의 범위 · 측정 방식을 사람이 읽는 설명으로 둔다. earth_moments 는 moment_kind(빛이 떠날 때 | 빛이 닿을 때) · time_kind(연도 | 년 전)로 나누고 year 는 사건 실제 연도다. 5장 출생 연도 연결은 사건 줄 없이 화면 계산만 한다(사건 3줄은 공개 제외). 사건 문장은 |빛이 떠난 해 − 사건 연도|(년 전 사건은 |years_ago − 광년|) ≤ max(빛 이동 시간 × 5%, 2년)일 때만 보이고, 빛이 닿을 때 사건은 대조하지 않는다. 날짜 · 올해는 한국 시각 기준
- 근거: 출처 값과 화면 표기를 분리해 반올림 규칙을 바꿔도 데이터를 다시 넣지 않는다. 가까운 별의 "빛이 떠난 해"는 해마다 1년씩 밀려 고정 사건과 2~3년 뒤 어긋나므로 데이터로 박제하지 않는다. 허용 범위는 먼 천체의 거리 오차(수 %)를 받아 주고, 가까운 천체는 최소 2년으로 연도 경계 흔들림만 허용한다
- 대안: 반올림 · 한글 표기 값을 저장 — 규칙 변경 때 재입력 필요, 출처 값과 대조 불가로 기각 · 빛 이동 시간 칸 저장 — 계산 가능한 값의 중복, 기각 · 가까운 별 사건 3줄 공개 — 해마다 어긋나 숨김이 늘어 기각 · 고정 허용(±N년) — 가까운 별과 먼 은하에 한 값을 쓸 수 없어 기각

## D-32 스토리 이미지 라이선스 확대: 퍼블릭 도메인 · CC0 · CC BY 4.0 (D-25 대체) (2026-10-09)
- 결정: 허용 = 퍼블릭 도메인 · CC0 · CC BY 4.0(크레디트 · 라이선스 표시 필수). CC BY 4.0 은 이미지 페이지 크레디트를 고치지 않고 그대로 작가 칸에 두고, 그림 아래 한 줄 · 크게 보기 · 출처 절에 크레디트 · 라이선스 · 출처 링크를 함께 보인다. 유지 = 알아볼 수 있는 실제 인물 사진 금지 · 상표 노출 금지 · AI 생성 자료 금지 · 직접 서빙 webp 480/960 · 장당 80KB 이하. 이미지 페이지에서 크레디트 · 라이선스를 직접 확인하지 못한 이미지는 넣지 않는다
- 근거: 2편 6~8 · 11장 사진 후보가 대부분 NASA · ESA 공동 크레디트(ESA/Hubble 공개 이미지는 CC BY 4.0)라 퍼블릭 도메인만으로는 채울 수 없다
- 대안: 퍼블릭 도메인만 유지하고 해당 장은 사진 없이 둠 — 장면의 실제 모습을 보여 줄 수 없어 기각 · NASA 단독 크레디트 사진만 찾기 — 같은 천체의 대표 사진이 대부분 공동 크레디트라 후보가 거의 없어 기각 · CC BY-SA 까지 허용 — 동일 조건 변경 허락 의무가 화면 · 파생물 범위를 모호하게 해 기각 · 외부 이미지 링크(핫링크) — 직접 서빙 · 용량 기준과 맞지 않아 기각

## D-35 이야기 입력 장치 삭제 · 1편 퀴즈 삭제 · 발행 계약 question 삭제 (D-33 전체 · D-31 5장 출생 연도 부분 대체) (2026-10-10)

- 근거: 입력 칸은 대부분의 방문자가 건너뛰고, 입력 전후 두 상태의 문구 · 대조 유지 비용이 든다 · 퀴즈 답이 바로 다음 장면에서 드러나 중복 · 이야기 문구는 코드에, 발행 파일은 데이터 판과 목록 정보만.
- 대안: 기존 입력 장치 유지 + 새 상호작용만 합의제(D-33) — 입력 칸의 유지 비용이 남아 기각.

## D-36 2편 장 문구를 보는 사람 기준으로, 천체 이름은 통용 이름으로 (2026-10-10)
- 결정: 2편(빛의 나이) 장 문구를 "빛이 떠난 지 ~" 대신 "우리가 보는 X는 ~ 전의 모습" 처럼 보는 사람 기준으로 쓰고, 천체 이름은 통용 이름(플레이아데스 성단 · 안드로메다은하 등)을 쓴다. 옛 우리말 이름(좀생이별 · 객성 등)은 기록 · 설화 맥락에서만 괄호로 병기한다.
- 근거: 빛 기준 문장은 "지금 보는 것이 과거 모습"이라는 결론을 읽는 사람이 스스로 이어 붙여야 한다(1장만 보는 사람 기준이라 6장부터 연결이 끊김). 낯선 옛 이름은 이해를 막는다.
- 대안: 빛 기준 유지 + 설명 문장 추가 — 장마다 문장이 길어져 기각.

## D-37 관리자 이야기 등록 · 미리보기 · 발행 · 되돌리기 (2026-10-10)
- 결정: 이야기 파일(stories/{story}.json) · 목록(stories/index.json)을 관리자 화면에서 발행한다. 등록 가능한 이야기와 쓰는 묶음은 백엔드 registry(admin_stories/registry.py) 상수가 정하고, 관리자는 묶음별 공개 판 · 제목 · 요약만 고른다. 두 파일은 같은 폴더 임시 파일 → os.replace 로 덮어쓴다(D-29 불변 원칙의 예외: 이야기 파일은 이름으로 공개되고, 가리키는 데이터 파일은 불변이라 옛 조합도 일관됨). 발행 · 재시도 · 되돌리기는 전역 잠금 행(story_publish_lock) FOR UPDATE 를 첫 문장으로 잡고 판 기록 → 두 파일 교체 → 상태 기록까지 쥔다(목록은 DB 전체로 만들므로 교체 순서 역전 방지). 이야기 파일 published_at = 이 판 발행 시각, 목록 published_at = 처음 공개된 시각(목록 순서 기준, 이후 바꾸지 않음). 되돌리기 = 이전 공개 판 내용으로 새 판 발행. 발행 전 문구 대조는 경고만 보인다. 미리보기 = 공개 페이지와 같은 컴포넌트에 관리자 판 내용 API(/api/admin/datasets/{slug}/versions/{n}/content)를 출처로 넘긴다.
- 근거: 서버가 임의 이름 파일을 쓰지 않게 막는 것이 핵심 · 상태 개념을 늘리지 않음 · 긴급 정정을 막지 않음 · 공개 route 에 관리자 경로를 섞지 않음.
- 대안: 클라이언트가 보낸 이야기 목록 신뢰 — 임의 경로 쓰기 위험으로 기각 / 공개 판 포인터로 되돌리기 — 상태 개념 증가로 기각 / 대조 불일치 시 발행 차단 — 긴급 정정 방해로 기각 / 미리보기를 공개 route 의 쿼리 모드로 — 공개 페이지에 관리자 경로가 섞여 기각.
- 보완(1R): failed 판은 발행 · 되돌리기를 막지 않음 · 최신 done 판 공개 파일 다시 쓰기 · 공개 파일 불일치 표시
- 외부 검토: A / 1R 지적 7건 중 수용 7건 · 2R 지적 2건 중 수용 2건

## D-38: 관리자 데이터 묶음 용어 — "발행 · 공개" → "판 · 판 확정" (2026-10-10)
- 결정: 관리자 화면 용어에서 "발행 · 공개"는 이야기(방문자 화면을 바꾸는 동작)에만 쓴다. 데이터 묶음은 "판"으로 통일하고 판 만들기는 "판 확정", 상태 done 은 "확정됨", 공개 제외는 "판에서 제외"로 부른다. 내부 이름(API · 상태값 · 파일명)은 바꾸지 않는다.
- 근거: 데이터 묶음의 [발행]은 방문자 화면을 바꾸지 않는데 같은 낱말을 써서 운영 흐름이 오해됨(실사용 중 "데이터 발행 후에도 공개 화면은 그대로" 설명이 필요했음). 데이터 묶음 쪽은 같은 대상을 기록본 · 판 · 공개 판 · 발행 · 공개됨 다섯 이름으로 불렀음.
- 대안: 현행 유지 — 기각(한 낱말 두 뜻) / 내부 이름까지 변경 — 기각(화면 문제이며 API · DB 변경은 위험만 늘림)

## D-39: 스테이징 서버를 두지 않는다 — 새 이야기와 이어지는 변경은 공개 목록으로 켠다 (2026-10-10)
- 결정: 스테이징 서버를 두지 않는다. 공개된 이야기의 코드 변경 중 새 이야기와 이어지는 부분(예: 2편 → 3편 링크)은 공개 목록(index.json)에 새 이야기가 있을 때만 켜지게 만들어, 배포가 아니라 관리자 발행 순간에 공개되게 한다. 공개 화면 단독 수정은 로컬 운영형 확인 + sha 태그 롤백으로 대응한다.
- 근거: 서버 가용 RAM 약 3.4Gi · 운영자 1명 · 스테이징은 도메인 · 인증서 · DB 가 두 벌.
- 대안: 스테이징 서버 — 기각(비용 대비 효과 낮음)

## D-41: 4편(바다 밑의 도시들) 구조 · 데이터 · 3 · 4편 다음 이야기 링크 (2026-10-11)

## D-42: 5편(그가 실패작이라 부른 밤) 구조 · 렌더링 · 텍스처 크기 예외 (2026-10-11)
