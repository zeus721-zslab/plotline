# 기반 참고 문서 — 인프라 · CI/CD · 운영 점검 · 환경 함정 · 품질 평가 · 셋업
 
> 용도: 새 저장소의 `docs/` 아래 기반 문서로 둔다(커밋 가능). 서버 IP·절대경로·시크릿은 넣지 않았다 — 서버 경로는 `DEPLOY`(배포 디렉터리) · `GATEWAY_CONF`(gateway nginx 설정) 같은 표기로 쓴다.
> zslab-mall에서 실제로 운영하며 확정한 내용만 담았다. 그대로 복사할 코드가 아니라 "이 구조를 쓴다"는 설계 요약이다.

## 1. 공유 서버 인프라 재사용
- 단일 서버에 프로젝트별 서버 유저를 두고, 공유 인프라(DB · Redis · 검색 · gateway)를 함께 쓴다.
- **gateway nginx:** 모든 도메인의 80/443을 프록시하는 단일 설정 파일.
  - 편집은 **같은 inode 덮어쓰기만**(`cat new > GATEWAY_CONF`). `sed -i`·임시파일+rename은 inode가 바뀌어 컨테이너가 옛 설정을 계속 서빙한다.
  - 순서: 백업 → 덮어쓰기 → `nginx -t` → reload.
  - 같은 server 블록에 location이 여러 개 있다 — 수정 전 블록 전체를 확인한다.
  - 로그인·가입 같은 민감 경로는 `limit_req` zone으로 IP별 제한(zone은 여러 location이 공유할 수 있음).
- **인증서:** 도메인별 디렉터리 + certbot webroot 방식.
- **새 프로젝트 준비:** 서버 유저 생성(docker 그룹 · sudoers.d 440) → 도메인·인증서 → gateway server 블록 추가 → 공유 네트워크 연결.
- **확인 습관:** 운영 확인은 운영 서버에서 한다. 공개 도메인이 실제로 어느 컨테이너로 가는지 server 블록으로 확인한다(다른 프로젝트 도메인을 잘못 찍어 결함으로 오판한 사례 있음).
## 2. CI/CD (방식 A)
- **흐름:** main push → GitHub Actions에서 이미지 빌드 → ghcr.io push → 서버에 SSH로 pull · `up -d --no-build --wait`.
- **변경 영역만 빌드:** paths-filter로 서비스별 판정 · buildx gha 캐시는 서비스별 scope.
- **태그:** `sha-<7자>` + `latest`. 서버는 빌드하지 않는다.
- **보존:** 패키지별 최근 N개 버전 유지(태그 없는 중간 버전 포함). provenance를 끄면 빌드 1회 = 버전 1개.
- **배포 직렬화:** concurrency로 동시 배포 방지.
- **롤백:** 서버 .env의 서비스별 이미지 태그 변수를 이전 sha로 지정(미설정 시 latest).
  - ⚠ 한쪽만 바뀐 커밋은 **다른 패키지에 그 sha 태그가 없다.** 롤백 대상 태그는 패키지별로 실제 존재 여부를 확인한다(`docker manifest inspect` 또는 GitHub Packages 화면). 규칙: "각 패키지에서 대상 시점 이전 가장 최근 sha 태그".
- **테스트 게이트는 PR CI**(이미지 빌드는 테스트를 돌리지 않음).
- **서버 소스:** sparse-checkout으로 필요한 디렉터리만 유지.
- **배포 시 env 점검:** .env와 .env.example 키 집합 비교 → 불일치는 경고(배포는 계속).
## 3. .env 키 동기화
- 원칙: 로컬·운영 모두 `.env` 키 집합 = `.env.example` 키 집합(값은 환경별).
- 점검 스크립트(sh·ps1)로 "example에만 있음 / env에만 있음"을 출력. 배포 워크플로에서도 호출.
- 새 키는 .env.example에 빈 값 + 주석으로 먼저 추가 → 각 환경 .env에 투입.
- .env 백업은 작업 트리 밖(또는 git 제외 등록된) 보관함에, 권한 600, 작업이 끝나면 정리(shred). 평문 사본을 쌓아 두지 않는다.
## 4. 운영 감시 (health-alert 패턴)
- **구조:** 서버 cron(15분)이 점검 스크립트 실행 → 이상 시 GitHub `repository_dispatch` → 알림 전용 워크플로가 실패로 끝남 → GitHub Actions 실패 메일. 외부 감시 서비스·메일 서버 없이 알림 경로를 만든다.
- **점검 항목 예:** 공개 페이지 200 · 컨테이너 health · 백엔드 내부 헬스 · 직전 실행 이후 ERROR 로그 줄 수.
- **스크립트 원칙:** 설정은 환경변수 · 시크릿·절대경로 기본값 금지 · `DRY_RUN=1` 지원 · 상태 파일·로그는 umask 077 · cron이 만든 로그 권한도 600으로 맞춘다.
- **워크플로 원칙:** 페이로드는 `${{ }}`로 run 스크립트에 직접 넣지 않고 env로 받아 출력(스크립트 인젝션 방지) · permissions 최소.
- **토큰:** fine-grained · 해당 저장소 한정 · Repository permissions → **Contents: Read and write**(repository_dispatch에 필요). UI에서 저장소만 고르고 권한을 추가하지 않으면 공개 저장소 읽기 전용으로 저장되어 403이 난다.
- **메일 수신:** GitHub Settings → Notifications → System → Actions에서 Email + 실패만 알림을 켠다.
- **한계:** 서버 자체가 멈추면 cron도 멈춘다 → GitHub 예약 점검(best-effort, 누락 많음)만 남는다. 로그 수집 파이프라인 중단은 별도 점검 항목이 필요하다.
## 5. 운영 서버 작업 원칙
- 첫 줄 "지금 그대로 실행" · 중단 조건 명시 · 읽기 전용 정찰과 변경 작업을 분리.
- 변경 전 백업 → 원복 절차를 지시서와 보고에 함께 남긴다.
- umask 077 · 값(시크릿) 출력 금지 · 보고에 절대경로 대신 표기 사용.
- 배포 디렉터리가 서버 유저 홈 자체일 수 있다 — 보관함·임시 폴더를 만들 때 git 작업 트리 안인지 확인하고, 안이면 `.git/info/exclude`로 제외한다.
- 로그인 회귀 확인 시 CSRF 토큰을 먼저 받고, 로그인 요청 수는 rate limit을 고려해 최소화한다.
- vi로 시크릿을 붙여 넣으면 `.viminfo`에 남을 수 있다 — 입력은 `read -rs` 방식이 안전하다.
## 6. 환경 함정 (Windows · Docker · 공통)
| 함정 | 증상 | 대응 |
|---|---|---|
| BOM | `Out-File -Encoding utf8`이 BOM 삽입 | `[System.IO.File]::WriteAllText(path, text, (New-Object System.Text.UTF8Encoding($false)))` |
| PowerShell 콘솔 한글 깨짐 | 출력만 깨져 보임(파일은 정상) | 파일 손상으로 오판하지 말고 Read 도구로 재확인 |
| 대괄호 경로 | PowerShell이 `[id].vue`를 와일드카드로 해석 | `git add -- "path/[id].vue"` |
| 호스트 vs 컨테이너 명령 | 호스트 npm으로 테스트 → 변환 단계 대량 실패 | 규정 컨테이너 명령만(`docker exec <frontend> pnpm …`) |
| 프론트 watcher | Docker 볼륨에서 새 디렉터리 미감지 | 프론트 컨테이너 재시작 |
| node_modules 익명 볼륨 | 호스트 사본이 lock과 버전 불일치(IDE 타입) | 컨테이너 → 호스트 복사, Windows는 `docker cp` 심볼릭 링크 실패 → Git Bash `tar -h` 파이프 |
| pnpm storeDir 절대경로 | 워크스페이스 설정이 환경변수보다 우선 | CI에서 `--config.store-dir` CLI 플래그로 덮어쓰기 |
| 전체 테스트 hook 타임아웃 | 대량 병렬 실행 시 setup 30초 초과 | 단독 실행으로 판정 후 이월(코드 결함과 구분) |
| hosts 파일 | 운영 도메인을 127.0.0.1로 돌려 둔 상태 | 로컬 브라우저 확인 전 hosts 상태 확인 |
| 대기 명령 | 고정 sleep은 불안정 | 조건 폴링(`until <check>; do sleep 2; done`) |
 
## 7. 품질 평가 틀 v3 (자체 평가용)
- **영역·배점:** 보안 35 · 디자인/UX 35 · 운영·개발 용이성 30 (프로젝트 성격에 맞게 조정 가능, 단 착수 전에 고정).
- **방식:** 영역별 100점에서 심각도 감점 — 치명 −25 · 높음 −10 · 중간 −4 · 낮음 −1 · 영역 하한 0 · 같은 원인은 1건(가장 큰 영향 기준) · 총점은 환산 합을 소수 1자리로.
- **심각도 기준 예:** 높음 = 핵심 흐름에서 사용자가 막힘 / 장애 시 복구 수단 없음 · 중간 = 우회 가능하지만 불편 / 운영자가 수작업으로 메워야 함 · 낮음 = 사소한 불일치·문구.
- **범위 예외:** 포트폴리오 성격상 감점에서 뺄 항목(예: 공개 데모 관리자 로그인, 서버 밖 백업)은 착수 전에 문서로 확정.
- **처리 규칙 (c):** 지적 전제 오류 = 감점 제외 · README 공개(문서화) = 감점 유지 · 부분 해소 = 남은 결함을 같은 심각도 정의로 재등급.
- **진행:** 평가 → 치명·높음 수정 → 고친 것만 재확인. 마지막 채점을 "마지막 탐색"으로 정하고, 재채점에서는 새 결함을 찾지 않는다. 채점 중 관찰된 잔여 사항은 공식 점수와 분리해 참고로 둔다.
- **독립성:** 자기 채점은 후해지므로 고위험 영역은 외부 검토로 보완한다.
